# Step 2 — Renderer Prototype and Benchmark

Execution plan for `docs/roadmap.md` step 2. The goal is to compare renderer
candidates on a representative set of workloads before committing to one.

## Goal

Answer the roadmap's question: *which renderer meets the performance and
platform-reach bar without undermining other commitments?*

This is a comparative evaluation, not the editor's renderer. The output is
evidence (numbers + notes), a tentative renderer choice, and the seed of a
`Renderer`/`View` abstraction that step 7 will stress-test.

## Scope

In scope:
- A `Renderer` trait in `src/view` with multiple backends.
- A benchmark harness driving each backend through the same workload.
- A set of hand-authored fixtures covering the shaping paths we care about.
- Per-fixture metrics: frame time (p50/p99), peak RSS, CPU%.

Out of scope (deferred to later steps):
- The real `TextBuffer` and editable buffer model (step 4).
- IME composition state (step 3) — fixtures are static text.
- Tree-sitter / real syntax highlighting. Fixtures are hand-tokenized into
  colored segments; no parser is pulled in.
- A real `View` trait with scroll/cursor/selection state — the renderer trait
  here is the minimal seed, not the step-7 surface.
- Cross-platform availability matrix (macOS only, per step 1).
- Cold-start measurement (noisy and not load-bearing for the choice).

## Candidates

Three backends, compared on identical workloads:

1. **wgpu + cosmic-text** — low-level GPU via wgpu, shaping/layout via
   cosmic-text (which uses rustybuzz, the HarfBuzz port). This is the
   "build it ourselves" path and exposes the most about where the hard
   problems live.
2. **wgpu + direct HarfBuzz (rustybuzz) shaper** — a thinner shaping layer
   on top of wgpu, without cosmic-text's retained-mode layout machinery.
   Measures how much cosmic-text helps vs. costs. (Implementation note: if
   this turns out to be a thin wrapper over cosmic-text's own internal
   shaper, we may fold it into candidate 1 and document that as a finding.)
3. **skia** (`skia-safe`) — mature, batteries-included, built-in text
   shaping. The "what does a production renderer give us for free?"
   baseline.

`gpui` is intentionally excluded. It is a full UI framework rather than a
renderer, and the roadmap flags that it "couples the project to Zed's
architectural choices and licensing trajectory" — it would also defeat the
step-7 "no internal path" investigation by handing us a black box. The
exclusion is itself a finding worth recording.

Each backend lives in `src/view/backends/` and is compiled in
unconditionally. This is a benchmark, not the production release — link
cost and binary size don't matter, and skipping feature gating means
benchmark runs don't trigger rebuilds when switching backends. The backend
is selected at runtime via a `--backend` flag.

## Fixtures

Hand-authored, version-controlled under `bench/`. Each is a text file paired
with a tokenized representation (either a sidecar file or a header) giving
the style segments per line. Segments carry both color and font style
(bold/italic) so that the source fixtures exercise the multi-attribute
shaping path each renderer exposes. Where styles are not load-bearing
(Arabic, emoji, minified), the fixture is monochrome and plain.

| # | Fixture | Size | Stresses |
|---|---|---|---|
| 1 | Real Rust source | ~2k lines | Baseline realistic case: multi-color segments with bold/italic (keywords bold, comments italic, strings colored, etc.), ASCII, mix of line lengths |
| 2 | Tiled Rust → 1M lines | 1M | Visible-range culling, scroll-offset handling, peak RSS, sustained throughput |
| 3 | Chinese markdown | ~1k lines | CJK wide glyphs, column alignment, mixed CJK+ASCII |
| 4 | Arabic prose | ~500 lines | BiDi reordering, contextual shaping, RTL paragraph direction |
| 5 | Emoji-heavy chat log | ~1k lines | ZWJ sequences, variation selectors, wide emoji, mixed scripts |
| 6 | Very long single lines (minified JS) | ~50 lines × ~5k chars | Horizontal scroll, line-wrap behavior, shaping of huge runs |

Fixtures 3–5 are a deliberate head-start on step 3 (IME/BiDi/wide-char); the
same fixtures will be re-run against the surviving renderer(s) there.

The 1M-line fixture is generated by tiling fixture 1; it is not checked in
as 1M lines but produced at startup from the smaller sample.

## Workload

- Fixed advancing scroll offset: each frame advances the offset by a fixed
  delta (e.g. one line per frame, capped at the buffer end where it wraps)
  and re-renders. No input handling, no real interaction.
- Visible range is computed from the offset and the window height; only
  visible lines (plus a small overscan) are passed to the renderer.
- Run duration: 5 seconds per fixture per backend. Long enough for stable
  percentiles, short enough to iterate.
- Window size: fixed (e.g. 1200×800), not resizable during the run.

## Metrics

- **Frame time** (p50, p99) — measured per frame via `Instant`, aggregated
  at end of run. The primary signal.
- **Peak RSS** — sampled periodically during the run (via `sysinfo`),
  tracking the maximum. Coarse but cheap; answers "does the renderer hold
  the whole buffer in GPU memory?".
- **CPU usage** — process CPU% averaged over the run (via `sysinfo`).
  Catches the "holds 120fps while pegging a core" failure mode.

All three are collected by the harness, not the backends, so backends stay
ignorant of the measurement.

## Architecture

```
src/view/
  mod.rs              Renderer trait + backend selection
  bench.rs            workload, harness loop, metrics collection
  backends/
    mod.rs            unconditional re-exports
    wgpu_cosmic.rs    wgpu + cosmic-text
    wgpu_direct.rs    wgpu + rustybuzz (thin)
    skia.rs           skia-safe (built-in shaping)
    stub.rs           no-op backend for harness validation
```

### Renderer trait (minimal seed)

```rust
pub struct Segment<'a> {
    pub text: &'a str,
    pub color: u32,      // 0xRRGGBB
    pub bold: bool,
    pub italic: bool,
}

pub trait Renderer {
    fn init(&mut self, window: &Window) -> Result<()>;
    fn resize(&mut self, width: u32, height: u32);
    fn render_frame(&mut self, offset: usize, visible: &[Vec<Segment>]) -> Result<()>;
    fn teardown(&mut self);
}
```

`visible` is the list of lines currently on screen, each as a list of
styled segments. The trait is intentionally narrow; it grows during step 7
into the full `View` surface. Bold/italic on the segment forces every
backend to exercise its multi-attribute shaping path, not just color runs.

### Harness

A separate binary (`bench` example or `[[bin]]`) that:
1. Loads a fixture.
2. Opens a window (winit).
3. Constructs the selected backend.
4. Runs the workload loop for the configured duration, collecting metrics.
5. Prints a one-line summary per run.

Output is plain stdout for now; no file logging or charts.

## Findings to capture

Per backend, after the runs, record (in this document, not just in chat):
- Raw numbers per fixture.
- Constraints the backend imposes on the future `View` API.
- Any privileged path the backend would require (relevant to step 7's
  no-internal-path commitment) — a renderer that forces a backdoor into
  the buffer or shaping layer is itself a finding.
- Whether the backend survived BiDi/CJK/emoji fixtures without API-level
  surgery (feeds step 3).

## Execution order

1. ✅ Plan written (this document).
2. ✅ Renderer trait + harness skeleton + metrics collection (`sysinfo` dep).
3. ✅ Stub backend; validate the loop runs end-to-end and metrics look sane.
4. Fixture set authored under `bench/` (start with fixture 1; add the rest).
5. wgpu + cosmic-text backend.
6. wgpu + direct rustybuzz backend (or fold into 5 with a recorded finding).
7. skia backend.
8. Run all fixtures against all backends; record numbers in this document.
9. Decision: primary renderer, or "more than one survives, revisit after
   step 3".
10. Update `docs/roadmap.md` step 2 with ✅ markers.

Each step is a separate commit.

## Risks / things that may change the plan

- **skia build complexity** — `skia-safe` has a heavy native build. If it
  blocks iteration, we may run the wgpu candidates first and add skia in
  parallel rather than serially. Not a plan change, just sequencing.
- **cosmic-text API churn** — if its API forces a specific layout model
  that conflicts with our future `View` abstraction, that's a finding, not
  a plan change; record it and proceed.
- **Fixture 6 (minified JS)** — may surface renderer assumptions about
  line length that make the comparison unfair. If so, document the
  assumption and either adjust the fixture or note the caveat in the
  results; don't redesign the trait around it.

## Non-goals (explicit)

- No real editor functionality.
- No real `TextBuffer` (step 4).
- No real `View` with scroll/cursor/selection state (step 7).
- No IME (step 3).
- No persistence.
- No automated unit tests (per `AGENTS.md`: prototype phase, defer tests).
