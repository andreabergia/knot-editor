# Brainstorm a task into an execution plan

The invocation supplies the task and any relevant notes, either directly or by reference. Treat those as the starting brief, not as settled design. If the task itself is missing, ask for it.

1. Read the task and notes. Check `docs/architecture.md` and `docs/decisions.md` for existing boundaries and choices, then inspect only the subsystem references, code, roadmap entries, or prior plans needed to understand this task. Distinguish validated constraints from open decisions. While reading, record the concrete code seams the change touches: the files to add or modify, the existing patterns or modules to mirror, and the hooks (registration, lifecycle, persistence, shutdown) the work must plug into.
2. Discuss the central shape of the solution before writing the plan. Present the few consequential open points, plausible alternatives, tradeoffs, and a recommendation in short batches. Ask for the user's judgment where product behavior, ownership, or scope cannot be inferred. Continue the discussion until the important choices are agreed; keep implementation detail proportional to the decision at hand.
3. Once aligned, create a high-level plan in a new file under `docs/plans/`. When the task is an item of an existing index plan (for example a `D###` item of `docs/plans/daily-driver.md`), always write it to its own file named after the item, such as `docs/plans/d069-clean-slate.md`, however small the item is or whatever the index plan says. In the index plan, add only a one-line 🚧 link to the new file under the item, and never add design notes, findings, or checkpoints there. State the user-visible outcome, chosen design and boundaries, explicit exclusions, and the decisions still deferred. Split work into coherent, end-to-end checkpoints with concrete deliverables, relevant automated validation, and a review gate for each checkpoint. Give each checkpoint an **Implementation context** note that names the code seams from step 1 — files to add or modify, the existing pattern or module to mirror, and the integration hooks — with just enough detail that implementation can start without exploring the codebase broadly. Sequence checkpoints so review can change later work without undoing completed work.
4. Cross-check the plan against the agreed choices and repository instructions. Link the source task and relevant docs. Follow `docs/README.md` for documentation ownership. When focused plans own detailed execution, keep the parent plan to shared scope, ordering, dependencies, and links rather than repeating their deliverables and review gates. Keep design rationale in the plan while decisions are proposed; update `docs/decisions.md` only when a choice has been validated. Do not implement the plan as part of this skill unless separately requested.

Keep the conversation concise. Do not produce a detailed execution plan before the design discussion has resolved the material open points.
